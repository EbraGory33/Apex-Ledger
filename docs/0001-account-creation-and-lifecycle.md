# Feature Design: Account Creation and Lifecycle

**Status:** Proposed  
**Feature:** F-001 — Account creation and lifecycle  
**Owner:** ApexLedger backend

## 1. Purpose

Establish the first customer-facing building block in ApexLedger: a durable account identity that can own wallets and participate in future transfers. This feature deliberately does **not** create a wallet, issue APX, or write a ledger entry. Those responsibilities belong to subsequent Wallet and Ledger features.

## 2. Scope

### In scope

- Create an account with a stable, server-generated identifier.
- Retrieve an account by identifier.
- Change an account’s lifecycle state between `ACTIVE` and `SUSPENDED`.
- Record creation and state-change timestamps.
- Enforce input validation and domain invariants.
- Expose REST endpoints for the above use cases.

### Out of scope

- Authentication, authorization, and KYC.
- Wallet provisioning, balances, APX issuance, transfers, and ledger entries.
- Account deletion; accounts are retained for auditability.
- Database selection, JPA entities, schema migrations, or persistence implementation. The JPA starter remains commented out until persistence is intentionally introduced.

## 3. Decisions and constraints

| Constraint                          | Design response                                                                                      |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Modular monolith                    | Account code lives behind the `account` module boundary; no other module reaches into its internals. |
| Domain-first packages               | Business rules are framework-free domain code; HTTP and future persistence are adapters.             |
| Banking core precedes blockchain    | Account is implemented before Wallet, Ledger, and Transfer.                                          |
| Ledger is financial source of truth | Account lifecycle operations never change a balance or create financial journal entries.             |
| JPA deferred                        | The initial implementation uses an in-memory repository adapter suitable for development and tests.  |

## 4. Domain model

### Account

| Field         | Type            | Rules                                                          |
| ------------- | --------------- | -------------------------------------------------------------- |
| `id`          | UUID            | Generated by the server; immutable.                            |
| `displayName` | String          | Required after trimming; 1–120 characters. Not assumed unique. |
| `status`      | `AccountStatus` | `ACTIVE` or `SUSPENDED`; starts as `ACTIVE`.                   |
| `createdAt`   | Instant         | Set once at creation; immutable.                               |
| `updatedAt`   | Instant         | Set at creation and on every accepted state change.            |

`AccountStatus` is intentionally small:

- `ACTIVE`: eligible to own and use wallets when that feature exists.
- `SUSPENDED`: retained but ineligible for future wallet operations and transfers.

The only supported lifecycle transitions in this feature are:

```text
create ──> ACTIVE <──> SUSPENDED
```

Requesting the account’s current state is idempotent and does not change `updatedAt`.

## 5. Module and package shape

```text
com.apexledger.account
├── domain
│   ├── Account
│   ├── AccountId
│   ├── AccountRepository
│   └── AccountStatus
├── application
│   ├── CreateAccount
│   ├── GetAccount
│   └── ChangeAccountStatus
└── adapter
    ├── in.web
    │   └── AccountController
    └── out.memory
        └── InMemoryAccountRepository
```

`wallet`, `ledger`, and `transfer` may depend only on the account module’s published application/domain contracts—not on its web controller or repository adapter.

## 6. Use cases and API contract

### Create account

`POST /api/v1/accounts`

Request:

```json
{
  "displayName": "Ada Lovelace"
}
```

Successful response: `201 Created`

```json
{
  "id": "72f667ef-0953-4de2-8d75-87ee5194bdc2",
  "displayName": "Ada Lovelace",
  "status": "ACTIVE",
  "createdAt": "2026-08-06T15:30:00Z",
  "updatedAt": "2026-08-06T15:30:00Z"
}
```

The response includes `Location: /api/v1/accounts/{id}`.

### Retrieve account

`GET /api/v1/accounts/{accountId}`

Successful response: `200 OK`, using the same representation. A syntactically valid but unknown identifier returns `404 Not Found`.

### Change account status

`PUT /api/v1/accounts/{accountId}/status`

Request:

```json
{
  "status": "SUSPENDED"
}
```

Successful response: `200 OK`, using the same representation. A repeated request for the current status returns `200 OK` without modifying `updatedAt`.

## 7. Validation and error responses

All errors use this shape:

```json
{
  "code": "VALIDATION_ERROR",
  "message": "displayName must contain 1 to 120 non-whitespace characters",
  "traceId": "optional-request-correlation-id"
}
```

| Situation                                  | HTTP status | Code                 |
| ------------------------------------------ | ----------: | -------------------- |
| Missing, blank, or oversized `displayName` |         400 | `VALIDATION_ERROR`   |
| Malformed UUID                             |         400 | `INVALID_ACCOUNT_ID` |
| Unsupported or missing status              |         400 | `VALIDATION_ERROR`   |
| Account does not exist                     |         404 | `ACCOUNT_NOT_FOUND`  |
| Unexpected failure                         |         500 | `INTERNAL_ERROR`     |

Do not expose framework exception messages or repository details in responses.

## 8. Implementation notes

1. Keep `Account` constructors/factories responsible for normalization and invariants. Controllers validate request shape but do not own business rules.
2. Inject a `Clock` and UUID generator (or `AccountIdGenerator`) so timestamps and identifiers are deterministic in tests.
3. The in-memory repository is a development adapter only. It must be concurrency-safe and clearly documented as non-durable.
4. Future persistence must implement the `AccountRepository` port and be introduced alongside a migration strategy; it must not leak JPA annotations into the domain model.
5. Future wallet creation must reject suspended accounts by querying the published account contract.

## 9. Acceptance criteria

- Creating an account with a valid display name returns `201`, a server-generated UUID, and `ACTIVE` status.
- Leading and trailing whitespace is removed before storage; an all-whitespace name is rejected.
- Fetching a created account returns exactly its stored identity, name, status, and timestamps.
- Suspending an active account updates its status and `updatedAt`, while preserving `id` and `createdAt`.
- Repeating a suspension is idempotent and does not change `updatedAt`.
- An unknown account returns `404`; malformed input returns the documented `400` error shape.
- No account operation creates APX, changes a balance, or writes a ledger entry.
- Unit tests cover domain invariants and transitions; web-adapter tests cover the three endpoints and error mapping.

## 10. Delivery slices

1. **Domain:** `Account`, status transitions, identifiers, clock-driven timestamps, and unit tests.
2. **Application:** create/get/change-status use cases with repository port and in-memory adapter.
3. **HTTP:** request/response DTOs, controller, validation, error handler, and adapter tests.
4. **Persistence later:** JPA adapter, schema migration, integration tests, and a decision to enable the currently commented JPA dependency.

## 11. Open questions

- What authentication principal or KYC reference should eventually be associated with an account?
- Is `displayName` a customer-facing legal name, a nickname, or both? If legal identity is required, model it separately rather than overloading this field.
- What audit-event mechanism should record administrative suspension once authorization is introduced?
