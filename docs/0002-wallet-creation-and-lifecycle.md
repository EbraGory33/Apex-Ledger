# Feature Design: Wallet Creation and Lifecycle

**Status:** Proposed  
**Feature:** F-002 — Wallet creation and lifecycle  
**Owner:** ApexLedger backend

## 1. Purpose

Provide a product-facing APX container owned by an account. A wallet is the identifier that future funding and transfer operations address; it is **not** a balance store. Financial balances and movements remain the responsibility of the Ledger feature.

This feature follows the completed Account feature and establishes the lifecycle rules that future Transfer operations must enforce.

## 2. Scope

### In scope

- Create a wallet for an existing active account.
- Retrieve a wallet by identifier.
- List wallets owned by an account.
- Freeze and reactivate a wallet.
- Persist wallets in PostgreSQL through the existing Flyway/JPA persistence baseline.
- Expose REST endpoints, validation, and consistent error responses.

### Out of scope

- Wallet balances, funding, APX issuance, transfers, holds, and transaction history.
- Ledger-account creation and journal entries.
- Deleting or permanently closing a wallet. Closing requires a future balance-zero rule enforced by the ledger.
- Authentication, authorization, KYC, and account ownership verification beyond the account identifier supplied to the API.
- Multi-asset support; this version supports APX only.

## 3. Decisions and constraints

| Constraint | Design response |
| --- | --- |
| Account comes first | A wallet must be associated with an existing `ACTIVE` account. Suspended accounts cannot create wallets. |
| Modular monolith | Wallet code owns its domain model, application services, persistence adapter, and HTTP adapter. |
| Ledger is financial source of truth | `Wallet` contains no balance, available-balance, decimal amount, or mutable financial total. |
| APX atomic units | Future amounts associated with a wallet use integer APX atomic units only; this feature has no amount field. |
| PostgreSQL/Flyway baseline | The schema change is a new Flyway migration; JPA entities are persistence adapters, not the domain model. |
| One account, many wallets | An active account may own zero or more wallets. |

## 4. Domain model

### Wallet

| Field | Type | Rules |
| --- | --- | --- |
| `id` | UUID | Generated by the server; immutable. |
| `accountId` | UUID | Required; immutable owner reference. |
| `label` | String | Required after trimming; 1–80 characters; unique per account, case-insensitively. |
| `assetCode` | String | Always `APX` in this version; immutable. |
| `status` | `WalletStatus` | Starts as `ACTIVE`. |
| `createdAt` | Instant | Set once at creation; immutable. |
| `updatedAt` | Instant | Set at creation and after an accepted status change. |

### Wallet status

- `ACTIVE`: eligible for future funding and transfer operations.
- `FROZEN`: visible and retrievable, but ineligible as either side of a future transfer.

The supported lifecycle transitions are:

```text
create --> ACTIVE <--> FROZEN
```

A request to set the current status is idempotent and does not change `updatedAt`.

### Invariants

- `accountId`, `label`, `assetCode`, and `createdAt` never change.
- A wallet can only be created when its owning account is `ACTIVE`.
- Labels are normalized by trimming whitespace. Uniqueness is evaluated using a case-insensitive normalized label within one account.
- An account can have wallets with the same label only when they belong to different accounts.
- A frozen wallet may be read but may not be used for future financial operations.
- Wallet state changes do not create journal entries and do not alter balances.

## 5. Module and package shape

```text
com.apexledger.wallet
├── domain
│   ├── Wallet
│   ├── WalletId
│   ├── WalletIdGenerator
│   ├── WalletRepository
│   └── WalletStatus
├── application
│   ├── CreateWallet
│   ├── GetWallet
│   ├── ListAccountWallets
│   ├── ChangeWalletStatus
│   ├── WalletNotFoundException
│   ├── DuplicateWalletLabelException
│   └── InactiveAccountException
└── adapter
    ├── in.web
    │   └── WalletController
    └── out.persistence
        ├── WalletEntity
        └── PostgresWalletRepository
```

The wallet application layer may query the account module through a published account-facing contract to determine whether an owner is active. It must not use account persistence entities or reach into account adapters.

The Ledger feature associates ledger accounts with a wallet through an explicit ledger-owned reference. Once F-003 is hardened, wallet-creation orchestration must provision the initial APX ledger account in the same transaction. The wallet domain remains independent of ledger implementation types; coordination occurs through a published ledger application contract.

## 6. API contract

### Create wallet

`POST /api/v1/accounts/{accountId}/wallets`

Request:

```json
{
  "label": "Primary wallet"
}
```

Successful response: `201 Created`

```json
{
  "id": "9dca4c11-526d-47ce-838b-f82ea6b38edf",
  "accountId": "72f667ef-0953-4de2-8d75-87ee5194bdc2",
  "label": "Primary wallet",
  "assetCode": "APX",
  "status": "ACTIVE",
  "createdAt": "2026-08-09T15:30:00Z",
  "updatedAt": "2026-08-09T15:30:00Z"
}
```

The response includes `Location: /api/v1/wallets/{id}`.

### Retrieve wallet

`GET /api/v1/wallets/{walletId}`

Successful response: `200 OK`, using the same representation.

### List an account's wallets

`GET /api/v1/accounts/{accountId}/wallets`

Successful response: `200 OK`

```json
{
  "items": [
    {
      "id": "9dca4c11-526d-47ce-838b-f82ea6b38edf",
      "accountId": "72f667ef-0953-4de2-8d75-87ee5194bdc2",
      "label": "Primary wallet",
      "assetCode": "APX",
      "status": "ACTIVE",
      "createdAt": "2026-08-09T15:30:00Z",
      "updatedAt": "2026-08-09T15:30:00Z"
    }
  ]
}
```

An existing account with no wallets returns `200 OK` with an empty `items` array. An unknown account returns `404 Not Found`.

### Change wallet status

`PUT /api/v1/wallets/{walletId}/status`

Request:

```json
{
  "status": "FROZEN"
}
```

Successful response: `200 OK`, using the wallet representation. Repeating a request for the current status returns `200 OK` without modifying `updatedAt`.

## 7. Validation and error responses

The feature uses the existing shared error envelope:

```json
{
  "code": "VALIDATION_ERROR",
  "message": "label must contain 1 to 80 non-whitespace characters",
  "traceId": "optional-request-correlation-id"
}
```

| Situation | HTTP status | Code |
| --- | ---: | --- |
| Missing, blank, or oversized label | 400 | `VALIDATION_ERROR` |
| Malformed account or wallet UUID | 400 | `INVALID_ACCOUNT_ID` or `INVALID_WALLET_ID` |
| Missing or unsupported status | 400 | `VALIDATION_ERROR` |
| Account does not exist | 404 | `ACCOUNT_NOT_FOUND` |
| Wallet does not exist | 404 | `WALLET_NOT_FOUND` |
| Account is suspended | 409 | `ACCOUNT_NOT_ACTIVE` |
| Label already exists for the account | 409 | `WALLET_LABEL_CONFLICT` |
| Unexpected failure | 500 | `INTERNAL_ERROR` |

Do not expose database constraint or framework exception text in HTTP responses.

## 8. Persistence design

Add a Flyway migration, for example `V2__create_wallets.sql`:

```sql
CREATE TABLE wallets (
    id UUID PRIMARY KEY,
    account_id UUID NOT NULL REFERENCES accounts(id),
    label VARCHAR(80) NOT NULL,
    asset_code VARCHAR(10) NOT NULL DEFAULT 'APX',
    status VARCHAR(20) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL,
    updated_at TIMESTAMPTZ NOT NULL,

    CONSTRAINT wallets_label_not_blank CHECK (length(trim(label)) > 0),
    CONSTRAINT wallets_asset_code_valid CHECK (asset_code = 'APX'),
    CONSTRAINT wallets_status_valid CHECK (status IN ('ACTIVE', 'FROZEN'))
);

CREATE UNIQUE INDEX wallets_account_label_unique
    ON wallets (account_id, lower(trim(label)));

CREATE INDEX wallets_account_id_idx ON wallets (account_id);
```

The database enforces referential integrity and duplicate-label protection. The application still checks those conditions to return intentional domain errors; the persistence adapter must translate a race-condition constraint violation to `DuplicateWalletLabelException`.

This is the F-002 APX-only schema. The F-003 hardening removes `wallets.asset_code` as accounting identity moves to `ledger_accounts.asset_code`; a wallet can then own one ledger account per supported asset. API compatibility may continue to report APX while it is the only enabled asset.

## 9. Implementation notes

1. Keep validation and state transitions in the framework-free `Wallet` domain type.
2. Use injected `Clock` and `WalletIdGenerator` dependencies, matching the Account feature's deterministic-testing approach.
3. Define a small account-facing port such as `AccountStatusLookup`; do not make wallet depend directly on `AccountRepository` or any account adapter.
4. Register the wallet persistence adapter through configuration, alongside the current PostgreSQL account adapter.
5. Do not add a `balance` column, calculated field, or wallet-level amount API. Balance arrives only with the ledger query design.
6. Do not use JPA cascade persistence from Account to Wallet. Each module owns its own repository and transaction boundary.

## 10. Acceptance criteria

- Creating a wallet for an active account returns `201`, a server-generated UUID, `APX`, and `ACTIVE` status.
- Creating a wallet for an unknown account returns `404`; creating one for a suspended account returns `409`.
- Labels are trimmed, cannot be blank or longer than 80 characters, and are unique per account without regard to letter case.
- The same normalized label is permitted for wallets of different accounts.
- Retrieving a wallet and listing an account's wallets return the stored immutable ownership and lifecycle data.
- Listing an existing account with no wallets returns an empty list.
- Freezing and reactivating a wallet update `updatedAt`; repeating the same requested status does not.
- The migration enforces the account foreign key, APX-only asset code, valid statuses, nonblank labels, and per-account normalized label uniqueness.
- No endpoint returns or mutates a wallet balance, and no wallet action creates a ledger entry.
- Unit tests cover domain invariants and transitions; application tests cover account-state and duplicate-label rules; web and PostgreSQL integration tests cover endpoints, migration constraints, and race-condition translation.

## 11. Delivery slices

1. **Domain:** Wallet value types, normalization, state transitions, and unit tests.
2. **Persistence:** Flyway migration, entity/mapper, PostgreSQL repository, and integration tests.
3. **Application:** create/get/list/status services, account-status lookup port, and domain error mapping.
4. **HTTP:** controller, DTOs, validation, shared error mapping, and endpoint tests.
5. **Ledger follow-up:** atomically provision the initial APX ledger account for each new wallet, backfill existing wallets, and derive wallet balances from balanced journal entries.

## 12. Open questions

- Should wallet labels be user-visible names only, or should a non-editable public wallet address be introduced separately before external transfers?
- Should freezing be available to the account owner, administrators, or both once authorization exists?
